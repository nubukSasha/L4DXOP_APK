# Известные особенности, унаследованные от `tool.py`

Этот документ описывает расхождения и ограничения, которые **намеренно сохранены**
при переносе логики из `tool.py` в `core/`. Ничего не «чинилось» без вашего решения,
потому что задача была — перенести логику 1-в-1.

---

## 1. SM4 в `tool.py` не соответствует стандарту GB/T 32907

**Симптом.** `core.crypto.SM4` не проходит эталонный тест-вектор из GB/T 32907-2016:

| | Значение |
|---|---|
| key = plaintext = `0123456789ABCDEFFEDCBA9876543210` | |
| Эталон GB/T (A.1) | `681EDF34D206965E86B3E94F536E4246` |
| `tool.py` / `core/` | `077ACBFDF01515D6135F18BBEB83DB05` |

**Причина.** В `tool.py` используются **нестандартные таблицы**:

* `SM4._S_BOX` — перестановка 0..255 (это корректно), но она **не равна** каноническому
  S-box SM4. Первые элементы: `34 66 25 74 89 78 E4 A9 ...` вместо `d6 90 e9 fe cc e1 ...`
* `SM4._CK` — расходится с формулой стандарта `ck_i = 0x00070e15 + 0x1c1c1c1c·i`:
  первые элементы `0xeb92b, 0x3a0ae783, 0x9e3b5c67, ...` вместо
  `0x70e15, 0x1c232a31, 0x383f464d, ...`.
  Это не циклический сдвиг стандартной таблицы — наборы значений разные.

`core/crypto.py` содержит **побайтово ту же** реализацию (проверено сравнением AST
с `tool.py` — см. `tests/test_core.py`, тест «SM4 regression vector»).

**Что это значит на практике.**

* Если ваши PAK используют **именно этот** вариант SM4 — всё работает, как работало
  в `tool.py`.
* Если игра использует стандартный SM4 (GB/T) — файлы с `encryption_method` 2, 4 и 31+
  будут читаться как мусор, а сборка PAK даст битый файл.

**Как проверить у себя.** Распакуйте PAK, у которого `detect_dominant_style()`
возвращает `enc_method` 2/4/31+ и `encrypted=True`. Если файлы распаковываются в
читаемый текст — вариант SM4 совпадает с игровым.

**Если понадобится исправить** — замените `SM4._S_BOX` и `SM4._CK` в
`core/crypto.py` на канонические таблицы GB/T 32907-2016. Больше нигде ничего менять
не надо: `PakCrypto._derive_sm4_key`, `_decrypt_sm4`, `encrypt_plaintext`,
`generate_block_indices` — обёртки, они останутся как есть.

## 2. `zuc_keystream()` использует фолбэк, а не настоящий ZUC

В `tool.py` сначала пробуется `gmalg.ZUC(...)`, а при `ImportError` возвращаются
16 констант. Библиотека `gmalg` не собирается под Android, поэтому в `core/crypto.py`
реализован **только** фолбэк (по ТЗ приложения):

```python
@staticmethod
def zuc_keystream() -> List[int]:
    return list(ZUC_FALLBACK_KEYSTREAM)   # 16 констант из tool.py
```

Константы идентичны оригиналу (проверено). Это работает для большинства PAK,
но для части файлов индекс будет расшифрован неверно — симптом: PAK открывается,
а список файлов пустой или `Index hash mismatch`.

## 3. `inject_files` требует `version > 7` и зашифрованный индекс

`TencentPakFile.inject_files()` читает исходный индекс так:

```python
orig_index_decoded = PakCrypto.decrypt_index(bytes(raw_orig_index), self._pak_info)
```

Этот шаг **всегда** применяет расшифровку. Если у PAK индекс открытый
(`index_encrypted == 0`) и `version <= 7`, будут применены лишние XOR-операции,
`Reader` прочитает мусор и операция упадёт с `struct.error`.

Ровно так же ведёт себя `tool.py`. В приложении верхний уровень
(`core.pak_codec.inject_lua_into_pak`) ловит исключение и пишет `ERR ...` в лог
вместо краша.

Тест `inject: на открытом индексе падает (как в tool.py)` фиксирует это поведение.

## 4. `repack_pak_file_full` возвращает число файлов и кладёт отчёт в `last_file_rows`

В `tool.py` сводка обработанных файлов печаталась через `rich.Table`.
В `core` таблица недоступна, поэтому:

* возвращаемое значение осталось прежним — `int` (сколько файлов обработано);
* список `(path_in_pak, orig_size, stored_size)` пишется в
  `pak_file.last_file_rows` и дополнительно логируется построчно.

## 5. Папка результата: `RESULT/` вместо `PAK_RESULT/`

В `tool.py` выходная папка называлась `PAK_RESULT`. По ТЗ приложения — `RESULT/`.

Создаются **обе**:

* `RESULT/` — рабочая папка (`core.paths.RESULT_DIR`);
* `PAK_RESULT/` — legacy (`core.paths.LEGACY_RESULT_DIR`), чтобы старые результаты
  не потерялись и пути из старых инструкций продолжали работать.

Алиас `tool.py` → `RESULT_DIR` сохранён.

## 6. Декомпиляция требует JVM, которой на Android нет

`unluac.jar` — это Java-программа. В `core/compiler.py` поиск JVM идёт по цепочке:

1. `SOURCE/jdk*/bin/java` — если вы положите в `SOURCE/` распакованный JDK для Android;
2. `java` в `PATH` — если установлен Termux:API или вы в обычном Linux;
3. `/system/bin/app_process` — системный ART, попытка экспериментальная (сырой `.jar`
   без `classes.dex` обычно не загрузится);
4. ничего не найдено → в лог пишется
   `WARN Декомпиляция недоступна на этой сборке`, а `.std.luac` сохраняется
   как `.luac` — файл не теряется.

**Что работает всегда:** конвертация BGMI ⇄ std Lua 5.3 (`core/lua_codec.py`)
и пересборка в BGMI с сохранением заголовка и nibble-флага оригинала.

**Что требует `luac5.3`:** компиляция `.lua` → байткод. Без `luac5.3` в `SOURCE/`
шаг DECOMPILE делает конвертацию в `.std.luac`, а шаг RECOMPILE без `luac5.3`
работать не будет. Без оригинала в `LUA_ORIGINAL/` шаг RECOMPILE тоже
невозможен — `repack_to_pubg` берёт заголовок и nibble-флаг из оригинала.
Диагностика доступна на экране **SETTINGS**.

## 7. `zstandard` — опциональная зависимость

`core/compression.py` импортирует `zstandard` в `try/except`:

* есть пакет → `CM_ZSTD` / `CM_ZSTD_DICT` работают полностью;
* нет пакета → `ZSTD_AVAILABLE = False`, блоки ZSTD возвращаются как есть
  (ровно как при ошибке декомпрессии в `tool.py`), сборка с ZSTD кладёт
  несжатые данные.

В `buildozer.spec` пакет **не указан** в `requirements` (он тянет за собой
долгую сборку и часто падает в CI). Если он нужен — добавьте `zstandard` в
`requirements = ...` и проверьте локальный `buildozer android debug`.
